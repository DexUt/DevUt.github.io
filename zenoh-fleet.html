ZenohFleet

I built and tested a two-machine ROS 2 and Zenoh system with a robot running Ubuntu and a ground station running macOS. The robot publishes compressed camera frames and simulated odometry through zenoh-bridge-ros2dds. The ground station has no ROS 2 installation. It uses rosbags to decode the CDR messages, runs YOLOv8n on the incoming video, and sends a real serialized geometry_msgs/Twist message back to the robot. The robot’s control node logs whether it receives moving or stopped commands. The main result is that the bridge can carry existing ROS 2 CDR payloads to a client that does not use rclpy, while the return path still works when the client constructs the correct ROS 2 message type.

System Architecture

  • Robot: Ubuntu with ROS 2 Humble and three ament_python nodes. The camera node publishes a looping driving clip as sensor_msgs/CompressedImage at 10 Hz. The telemetry node publishes a simulated 2 m-radius circular trajectory as nav_msgs/Odometry at 5 Hz. The control node subscribes to /cmd_vel and logs received commands.
  • Bridge: zenoh-bridge-ros2dds runs in router mode on tcp/0.0.0.0:7447 and mirrors the ROS 2 topics onto Zenoh keys.
  • Ground station: Python processes on macOS open a Zenoh session, decode incoming messages, display the video, run object detection, and publish commands back to the robot. ROS 2 is not installed on this machine.

Payloads

  • The bridge performs no format translation. It forwards the bytes associated with each bridged key.
  • Robot to station: the station receives serialized ROS 2 messages in CDR format and decodes them with rosbags’ typestore.
  • Station to robot: the station creates a geometry_msgs/Twist, serializes it to CDR, and publishes it. A JSON payload would not be a valid /cmd_vel message.
  • ROS topics use CDR, while detections uses JSON and annotated_image uses raw JPEG as Zenoh-native payloads.

Tools

  • zenoh-bridge-ros2dds on the robot and the Eclipse Zenoh Python API on both machines.
  • ROS 2 Humble with three ament_python packages, rclpy, and colcon.
  • Python 3.11, rosbags, OpenCV, NumPy, Ultralytics YOLOv8n, and psutil on the ground station.
  • The system monitor uses Zenoh directly and does not depend on ROS 2.

Tested Scope

  • Implemented and tested on a clean LAN: camera and telemetry nodes, bridging, ROS-free CDR decoding on macOS, YOLOv8n inference, Zenoh-native detections and annotated video, the CDR-encoded cmd_vel return path, and the system monitor.
  • Demonstration only: the control node logs received commands. No motors are connected.
  • WAN resilience and performance relative to DDS were not measured. The current result is limited to the tested LAN setup.

Message Flow

The table shows the payloads, ROS 2 topics, and Zenoh keys used in the tested system.

On the robot, the camera and telemetry nodes publish standard ROS 2 topics. The bridge exposes those topics as Zenoh keys and forwards the serialized payloads. The ground station subscribes to the keys, decodes the messages, runs detection, and publishes the return command as a serialized geometry_msgs/Twist. Detection results, annotated frames, and system statistics use Zenoh-native keys.

Key Takeaways

Three conclusions from building and testing the communication path.

CDR works without ROS 2

  • The bridge forwards the serialized CDR payloads produced by DDS, so the macOS station can decode CompressedImage and Odometry without rclpy or a ROS 2 installation.
  • The same approach works in the other direction when the station creates and serializes a valid geometry_msgs/Twist.

Payloads and threads need explicit handling

  • ROS 2 topics use CDR, while detection results and annotated frames use Zenoh-native JSON and JPEG payloads.
  • Zenoh callbacks run in the background, so the macOS viewers pass frames through a single-slot queue before calling cv2.imshow() on the main thread.

Scope of the demonstration

  • The system was tested on one clean LAN. It demonstrates message interoperability and a working return path, not WAN resilience or performance relative to DDS.
  • Detection and annotated-image traffic currently passes through the Ubuntu bridge, and the control node only logs commands because no motors are connected.
